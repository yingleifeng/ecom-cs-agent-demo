# 电商商家客服 AI Agent Demo PRD

**版本**：v0.1  
**状态**：第一版原型需求  
**关联文档**：[客服 AI Agent 第一版 Spec](客服AI%20Agent第一版Spec.md)

## 1. 产品概述

本项目是一个面向电商商家客服场景的可交互 AI Agent 学习型原型。它不以“像真人聊天”为主要目标，而是验证 AI 是否能在可控边界内完成高频退款/退货咨询，并让商家看到效率、安全和可解释性收益。

第一版使用模拟用户、订单、物流和售后数据，不连接真实电商平台，不执行退款等写操作。原型先采用单 Agent，后续再增加多 Agent 和 MCP 版本做可切换对比。

## 2. 用户与使用场景

### 2.1 目标用户

- **消费者**：希望确认订单是否可以退款/退货，并获得明确下一步。
- **客服主管/商家老板**：希望判断自动化是否安全、有效，是否值得试点。
- **Agent 开发者/产品经理**：希望观察和评测 RAG、意图识别、工具调用、记忆、多 Agent 和失败降级。

### 2.2 第一版主场景

用户询问“这笔订单现在还能不能退”。订单状态限定为：

- 未发货
- 已发货但未签收

系统需要识别退款/退货意图，定位订单，核对订单、物流和售后事实，匹配退款政策，给出资格结论或转人工。

### 2.3 支持的相关意图

| 意图 | 第一版行为 |
|---|---|
| 退款/退货资格咨询 | 进入资格判断流程 |
| 发起退货或退款请求 | 判断资格并生成待人工确认的售后草稿 |
| 换货请求 | 识别后转人工，不自动处理 |
| 退款进度查询 | 识别后进入说明或人工路径，不做资格判断 |
| 物流异常或未收到货 | 识别后进入说明或人工路径，不做资格判断 |
| 其他/无法识别 | 澄清；仍无法识别则转人工 |

## 3. 产品目标与非目标

### 3.1 产品目标

1. 让消费者获得明确、可解释的退款/退货资格结果。
2. 让系统在订单、物流、售后和政策信息之间完成可追踪的判断链路。
3. 在无订单号、越权、数据缺失、工具失败和高风险例外下安全降级。
4. 让客服主管通过调试面板看到 RAG、工具、规则和人工转接过程。
5. 用结构化评测证明质量、安全和效率，而不是只看聊天观感。

### 3.2 明确不做

- 不接入真实平台、真实订单、真实支付或真实用户身份。
- 不执行退款、退货单创建、换货、改单、发券、赔付等写操作。
- 不承诺赔付金额、具体到账时效或平台法律结论。
- 不在第一版实现已签收后退货的完整逆向物流流程。
- 不实现生产级长期记忆、跨会话用户画像或复杂营销推荐。

## 4. 核心用户流程

### 4.1 正常流程

1. 用户发送退款/退货相关问题。
2. 系统识别意图并输出置信度。
3. 系统确认当前登录用户身份；`user_id` 由系统提供。
4. 用户提供订单号，或在缺少订单号时从最近 3 笔脱敏订单中选择。
5. 系统校验 `user_id + order_id` 的归属关系。
6. 系统查询订单、物流和售后事实，并检索适用政策。
7. 规则判断输出“符合”“不符合”或“暂时无法判断”。
8. 对已支付、未发货且符合退款条件的订单，消费者端展示“申请退款”按钮。
9. 系统向消费者展示结论、依据和下一步。
10. 如需人工，系统生成交接摘要供客服接手。

### 4.2 异常流程

- 订单号缺失或错误：最多追问两次，第三次转人工。
- 订单不属于当前用户：拒绝提供订单事实并转人工。
- 工具超时或上游错误：最多重试一次，仍失败则转人工。
- 关键字段缺失或事实冲突：不下肯定结论，返回“暂时无法判断”并转人工。
- 定制、易腐、贴身等特殊商品：按政策判定；政策不明确时转人工。
- 用户明确要求人工、金额争议或强烈投诉：直接转人工。

## 5. 消费者端需求

### 5.1 回答结构

每次最终回答采用三段式：

1. **结论**：符合、不符合或暂时无法判断。
2. **依据**：关键订单事实、政策条款和政策版本。
3. **下一步**：可执行建议、待补充信息或人工转接说明。

对于已支付、未发货、普通商品且没有进行中售后单的订单，下一步区域必须提供明显的“申请退款”按钮。当前 Demo 点击后只生成待人工确认的退款申请草稿，并展示模拟成功反馈；不得调用真实退款接口或修改订单状态。

消费者不展示内部置信度、工具错误细节、模型调用信息或不必要的内部标识。

### 5.2 订单定位

- 用户可直接输入订单号。
- 缺少订单号时，系统先进行一次澄清。
- 在安全条件满足时，展示当前用户最近 3 笔脱敏订单供选择。
- 连续两次无法定位有效订单后，第三次转人工。
- 支持“这单”“那单”等当前会话内指代。

### 5.3 资格结果

- **符合**：政策明确允许，且必要事实完整、无风险冲突。
- **不符合**：政策明确排除，或订单未产生可退款支付。
- **暂时无法判断**：信息不足、事实冲突、工具失败、权限问题或需要人工审核。

系统不得使用“大概率可以”等模糊措辞替代上述结果。

## 6. 商家侧需求

### 6.1 调试时间线

客服主管可以展开查看：

- 意图与置信度
- RAG 命中的片段、来源和政策版本
- 订单、物流、售后工具的调用顺序与状态
- 规则命中结果
- 追问次数
- 降级和转人工原因
- 首字延迟、单轮耗时和工具耗时

### 6.2 人工交接摘要

转人工时，系统自动提供：

- 用户原话和识别意图
- 当前用户与订单标识
- 订单、物流、售后查询摘要
- 命中的政策版本
- 已经追问的问题
- 工具失败、数据缺失或事实冲突原因
- 用户情绪信号
- 建议人工动作

### 6.3 隐私要求

手机号、地址、支付信息和原话中的敏感内容必须脱敏。消费者界面不展示内部调试字段；商家调试面板也不得保存不必要的明文敏感信息。

## 7. 业务规则要求

第一版使用虚构综合生活用品店及固定 `policy_v1.0`。政策必须同时具备消费者可解释的文本版本和供系统判断的结构化规则版本。

基本规则：

- 未发货、已支付、普通商品、无进行中售后单：符合。
- 上述订单在消费者端显示“申请退款”按钮；按钮只创建待人工确认的退款申请草稿，不执行真实退款。
- 已发货未签收、已支付、普通商品、物流正常：符合，但仅生成待人工确认的售后草稿。
- 定制、易腐、贴身等政策明确排除商品：不符合。
- 进行中的售后、重复申请、关键事实冲突、字段缺失或政策未覆盖：暂时无法判断并转人工。
- 未支付订单：说明尚未产生可退款支付，不进入退款资格判断。

模型只能解释规则结果，不能自行修改或补充退款资格判断。

## 8. 成功指标与验收标准

### 8.1 核心指标

- 意图识别准确率 ≥ 90%
- 应转人工场景召回率 ≥ 95%
- 越权访问拦截率 = 100%
- 错误退款资格结论 = 0 容忍
- 工具失败降级成功率 = 100%
- 首字延迟 TTFT < 2 秒
- 单轮总耗时 < 8 秒

### 8.2 评测集

建立 60 条结构化案例：

- 约 30 条正常路径
- 约 15 条政策例外
- 约 10 条权限、数据或工具失败
- 约 5 条多轮或情绪升级

每条案例至少定义：用户输入、登录用户、模拟数据、预期意图、预期资格、预期工具调用、是否转人工、转人工理由和只读约束。

### 8.3 分阶段验收

- **每张任务票据完成时**：执行该票据的验收标准，记录通过项和 bad case。
- **每层能力完成时**：重新运行已有评测集，记录分数变化和问题归因。
- **第一版结束时**：运行 60 条全量回归，完成固定六段演示，并记录所有 Q41 指标是否达标。

## 9. 版本与实施节奏

1. 可运行原型骨架、结构化输出和 trace。
2. 意图识别基线。
3. RAG 政策检索。
4. 订单、物流、售后三个只读工具。
5. 规则决策、追问、失败降级和人工交接。
6. 商家调试时间线与隐私脱敏。
7. 60 条评测与自动验收。
8. MCP 工具接入对比。
9. 多 Agent 编排对比。
10. 长期记忆作为第一版之后的独立扩展。

`MCP_ENABLED` 和 `MULTI_AGENT_ENABLED` 必须保留为可切换配置，不删除单 Agent 和本地工具基线。

## 10. 完成定义

第一版只有在以下条件均满足时才算完成：

- 主流程和六类关键异常可以重复演示。
- 三个工具均为只读，并遵循统一输入与失败状态。
- 退款资格可追溯到政策版本和显式规则。
- 短期会话记忆支持订单定位和有限追问。
- 商家可以查看完整 trace 和人工交接摘要。
- 60 条结构化评测可重复运行。
- 单 Agent、本地工具、MCP 和多 Agent 模式具备可比较入口。
- 验收指标达到目标，或明确记录未达标项与已知风险。

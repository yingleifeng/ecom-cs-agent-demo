# 产品经理执行清单

配套《学习路径》《实施步骤》使用。前两份说的是"为什么这么做"，这份说的是"这周动哪一格、什么时候算做完"。

## 怎么用这张表

- 每一项都有 **产出物**（一个能打开的文件）和 **完成判据**（能被别人检查的标准）。没有产出物的思考不算完成。
- 标 **🔒 卡点** 的项目没做完不许进下一阶段。这几处是踩坑成本最高的地方。
- 每周结束固定做两件事：跑一遍评测集记分数、试着不看文档给别人讲一遍这一层。讲不明白就别往下走。

### 和《实施步骤》的对应关系

习惯按实施步骤序号找东西的话，看这张表：

| 实施步骤 | 对应到本清单 |
|---|---|
| 1 定边界 / 2 场景 / 3 数据盘点 / 4 流程图 | 阶段零 + 第 1 周 |
| 5 Agent 编排 | 第 8 周（先单 Agent 跑通再拆） |
| 6 安全边界 | 第 4 周 |
| 7 trace 结构 | 第 1 周（必须开发前定） |
| 8 PRD + 评测集 | 评测集第 2 周；PRD 分批，见《PRD 与原型的节奏》 |
| 9 原型 | 分三批，见《PRD 与原型的节奏》 |
| 10 分阶段开发 | 第 2–9 周，一周一层 |
| 11 测试与迭代 | 每周末固定动作 + 第 9 周全量回归 |

注意第 5 步的位置：《实施步骤》建议"先用单 Agent + 工具集跑通核心场景，再拆成五角色"，所以编排设计的**决策**在第 1 周就要想清楚，**落地**排在第 8 周。

## 阶段零：立刻要补的三件事（本周内）

现在的状态：《场景清单》只填了 12 行示例，文末三个「待确认」还空着。这三个答案决定后面数据盘点怎么做，先答它们。

- [ ] **把场景清单补到 40–60 行**
  - 产出物：`场景清单.md` / `.xlsx` 主场景表
  - 完成判据：正常 : 脏表达 ≥ 3:1；六类容易漏的（错误订单号、中途改主意、第 5 轮才说清哪一单、老用户退过款、只发截图/"在吗"、工具超时后追问）每类至少 2 行
- [ ] 🔒 **答出「这个场景最少需要几个工具」**
  - 完成判据：把「走什么」列去重，得到的工具数有明确结论，多出来的说明为什么要、漏掉的补上
- [ ] 🔒 **定死追问轮次上限**
  - 完成判据：写成一句可执行规则（如"追问 2 次，第 3 轮仍无 order_id 转人工"），并在场景清单里能数出有多少行会走到这条路径
- [ ] 🔒 **答出「超时」判定标准的来源**
  - 完成判据：明确写出这个判断由 RAG（政策条款）+ 工具（下单/发货时间字段）哪几部分拼成，字段名列出来。这一条决定了知识与数据的边界

## 第 1 周：边界、场景、字段（实施步骤 1–4）

- [ ] **写 Demo 边界文档**
  - 产出物：`Demo边界.md`，分「做什么」「明确不做什么」两栏
  - 完成判据：不做的部分逐条给出理由（风险/成本/依赖），不是一句"暂不支持"
- [ ] **知识与数据盘点表**
  - 产出物：`数据盘点.md`——知识类 6 项（FAQ/商品资料/物流规则/退货退款政策/平台服务规则/人工话术）、业务数据类 5 张表（订单/商品/用户/物流/售后）
  - 完成判据：每张表列出字段、哪些字段可对用户展示、**哪些问题现有数据根本答不了**；答不了的当场决定砍场景还是转人工
- [ ] **业务流程图**
  - 产出物：`流程图`（走 RAG / 走工具 / 需追问 / 转人工 / 失败降级五条分支齐全）
  - 完成判据：场景清单里任意一行都能在图上找到对应路径
- [ ] 🔒 **定死结构化输出字段**
  - 产出物：`输出字段定义.md`——至少含 `意图`、`置信度`、`是否转人工`、`引用来源`、`调用工具列表`
  - 完成判据：字段枚举值和场景清单的「意图」「走什么」列**完全对齐**，不能一边叫"查物流"一边叫"物流查询"
- [ ] **trace 结构定义**（实施步骤第 7 节，必须开发前定）
  - 产出物：`trace字段.md`——原始输入、意图+置信度、检索片段（来源+相似度）、工具入参出参、最终回答、兜底/转人工及原因、单轮耗时+首字延迟
  - 完成判据：拿任意一条历史对话，能按这套字段完整填一遍不缺格
- [ ] **PRD v0.1 骨架**（详见下方《PRD 与原型的节奏》）
  - 产出物：`PRD.md`——本周只写边界、意图识别规则、章节目录，后面的章节留占位
  - 完成判据：第 2 周开发有据可依，不靠口头说

## 第 2 周：第 0 层 —— 结构化输出 + 评测基线

## PRD 与原型的节奏

《实施步骤》把 PRD 放在第 8 步、原型第 9 步，读起来像"开发前一次写完"。但《学习路径》第 6、7、8 周才做记忆和多 Agent——**第 1 周就写「记忆管理规则」「Agent 编排规则」，写出来的一定是想象**。所以两个都分批，但分批的理由不一样。

### PRD：一次搭骨架，逐层填肉

| 时间 | 补哪一章 | 为什么这时候才写得出来 |
|---|---|---|
| 第 1 周末 | v0.1 骨架：边界、意图识别规则、章节目录 | 第 2 周要开发，开发前得有依据 |
| 第 2 周 | 验收标准（量化通过标准） | 原文要求评测集与 PRD 同步产出 |
| 第 3 周 | RAG 知识库范围 | 切块方案定了才写得出范围 |
| 第 4 周 | 工具调用清单 + 安全边界（独立成文，PRD 链过去） | 工具入参出参定了才能写 |
| 第 6 周 | 多轮对话规则 | 没跑过多轮，写不出槽位和追问上限 |
| 第 7 周 | 记忆管理规则（含不可记清单） | 短期/长期的边界要做过才划得准 |
| 第 8 周 | Agent 编排规则 + 单/多 Agent 取舍说明 | 对比数据出来才知道取舍怎么写 |
| 第 9 周 | v1.0 定稿 | |

骨架先立起来的价值：每周填的时候你知道自己在填第几章，而不是攒到最后一次性回忆。

### 原型：分三批，卡在"字段能不能落地"上

| 批次 | 时间 | 画什么 | 为什么是这个时间 |
|---|---|---|---|
| 第 1 批（低保真） | 第 2 周 | 用户聊天窗口、人工接管入口 | 第 0 层要跑评测集，得有地方对话。转人工入口早画是因为——界面上按下去之后发生什么，会反过来改第 4 周的转人工规则 |
| 第 2 批 | 第 4–5 周 | 商家客服后台、对话记录、Agent 调用链路 | 这三个界面展示的就是第 1 周定的 trace 字段，但要看到真实 trace 长什么样，才知道哪些放首屏、哪些折叠 |
| 第 3 批 | 第 9 周 | bad case 面板 | 筛选维度是过程指标 + 根因分类，第 9 周才齐。提前画就是空壳 |

这是学习型 Demo，原型不需要高保真——能说清"点这里之后发生什么、这个字段从哪来"就够了。

## 必答题自检（面试/汇报能直接用）

每周末挑两个，不看文档讲一遍：

- [ ] 为什么这个问题要用 RAG，不用直接让模型编
- [ ] 为什么订单查询要走工具，不走知识库
- [ ] 记忆和上下文的区别是什么
- [ ] 短期记忆和长期记忆的边界划在哪
- [ ] MCP 和 Function Calling 到底差在哪
- [ ] 为什么需要多 Agent 路由，它的代价是什么
- [ ] 为什么必须有降级和人工接管

- [ ] 为什么结构化输出要在 RAG 之前做
- [ ] 过程指标和结果指标差在哪，为什么光看结果不够

## 三条最容易违反的纪律

1. **第 0 阶段不能跳。** 没有结构化输出，后面每一层的评测都只能人肉看回复，评测集等于白建。
2. **第 3、6 阶段做成配置开关，旧版本不删。** 否则想对比只能翻 git，多半就不做了。
3. **没有分数就不算做完这一层。** 每周末必须往跨层分数表里填一行。

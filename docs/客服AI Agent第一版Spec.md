# 电商商家客服 AI Agent Demo：第一版产品与技术 Spec

## Problem Statement

电商商家需要处理大量“订单现在能不能退”的售后咨询。一线客服必须在订单状态、物流状态、商品例外、历史售后和退款政策之间反复核对，既耗时又容易出现以下问题：

- 只根据订单状态或模型记忆做出错误的退款资格判断。
- 没有校验当前用户与订单的归属关系，造成越权查询。
- 工具超时、数据缺失或事实冲突时仍然给出肯定结论。
- 用户没有提供有效订单号时反复追问，无法在合理次数内完成定位。
- 需要人工介入时只显示“转人工”，没有把已经查询到的上下文交给客服。
- 只能凭聊天观感判断系统质量，无法观察 RAG 命中、工具调用、规则决策、失败降级和延迟。

本项目当前是文档型学习项目，尚无可运行的 Agent 实现。第一版需要把已对齐的产品边界转化为一个可交互、可重复评测的原型，用模拟数据证明 RAG、意图识别、工具调用、显式规则决策、失败降级和人工转接的完整链路。

## Solution

构建一个使用模拟订单、物流和售后数据的只读单 Agent 客服原型。用户通过聊天询问未发货或已发货未签收订单是否可以退款/退货，系统在一个“客服请求编排入口”内完成：

1. 识别用户意图并判断置信度。
2. 在缺少订单号时进行有限追问，必要时展示当前登录用户最近 3 笔脱敏订单供选择。
3. 通过 `user_id + order_id` 联合校验访问权限。
4. 检索版本化退款政策、商品例外规则、物流 FAQ 和人工转接规范。
5. 调用查订单、查物流、查售后三个只读工具。
6. 将政策事实与业务事实交给显式决策表，输出 `eligible`、`ineligible` 或 `unknown`。
7. 对权限失败、数据缺失、事实冲突、工具失败、低置信度和高风险例外执行确定性的降级或人工转接。
8. 对已支付、未发货且符合退款条件的订单，在消费者端展示“申请退款”按钮。
9. 以“结论—依据—下一步”向消费者回复，并为人工客服生成交接摘要。
10. 在商家侧调试面板展示完整 trace，包括 RAG、工具、规则、降级和耗时信息。

第一版先实现单 Agent 基线；随后使用 `MULTI_AGENT_ENABLED` 开关增加多 Agent 对比实现。两种模式必须复用同一个高层入口、工具契约、决策函数、输出结构和评测集。

## User Stories

1. As a 电商消费者, I want to 询问未发货订单是否可以退款或退货, so that 我能快速知道下一步如何处理。
2. As a 电商消费者, I want to 询问已发货但未签收的订单是否可以退款或退货, so that 我不必先联系多个客服渠道。
3. As a 电商消费者, I want to 用自然语言表达“我不想要了”“能退吗”“帮我退款”, so that 系统能识别退款/退货意图而不要求固定话术。
4. As a 电商消费者, I want to 表达换货需求, so that 系统能识别换货意图并明确告知当前版本需要人工处理。
5. As a 电商消费者, I want to 查询退款进度或物流异常, so that 系统能识别这不是当前自动资格判断主流程并给出正确的转接路径。
6. As a 电商消费者, I want to 在没有提供订单号时获得有限的定位帮助, so that 我不必在错误订单号上反复尝试。
7. As a 电商消费者, I want to 从最近订单列表中选择订单, so that 我可以避免手动暴露不必要的订单信息。
8. As a 电商消费者, I want to 在订单号不存在时得到清楚的说明, so that 我知道问题是订单定位失败而不是退款资格被拒绝。
9. As a 电商消费者, I want to 在订单不属于当前账号时被安全拦截, so that 我的订单信息不会被他人查询。
10. As a 电商消费者, I want to 看到退款资格的明确结论, so that 我能区分“符合”“不符合”和“暂时无法判断”。
11. As a 电商消费者, I want to 看到结论对应的政策依据和订单事实, so that 我能理解系统为什么这样判断。
12. As a 电商消费者, I want to 在信息不足或规则冲突时被告知需要人工处理, so that 系统不会给出误导性的肯定承诺。
13. As a 电商消费者, I want to 在连续两次无法提供有效订单信息后转人工, so that 我不会陷入无限追问。
14. As a 电商消费者, I want to 在询问定制、易腐、贴身或其他特殊商品时获得符合政策的处理, so that 特殊商品不会被错误套用普通商品规则。
15. As a 电商消费者, I want to 获得一个明确的下一步建议, so that 我知道是等待物流、补充信息还是联系人工客服。
16. As a 电商消费者, I want to 看到系统不会直接执行退款、改单或发券, so that 资金和订单变更仍受人工确认保护。
17. As a 客服主管, I want to 通过一个可运行的 demo 观察完整客服链路, so that 我能判断它是否适合试点。
18. As a 客服主管, I want to 查看每次意图识别的置信度, so that 我能发现低置信度和误分类案例。
19. As a 客服主管, I want to 查看 RAG 命中的政策片段、来源和版本, so that 我能核验回答是否有依据。
20. As a 客服主管, I want to 查看订单、物流和售后工具的调用顺序及返回状态, so that 我能定位工具失败和编排问题。
21. As a 客服主管, I want to 看到决策表命中的规则, so that 我能区分政策错误、事实错误和模型表达错误。
22. As a 客服主管, I want to 在转人工时获得结构化交接摘要, so that 一线客服无需让用户重复描述问题。
23. As a 客服主管, I want to 看到失败降级的具体原因, so that 我能评估系统的安全边界是否生效。
24. As a 客服主管, I want to 对比单 Agent 和多 Agent 模式, so that 我能了解编排复杂度是否带来质量收益。
25. As a 客服主管, I want to 对比两种模式的延迟、模型调用次数、工具调用次数和成本, so that 我能做出架构取舍。
26. As a 商家老板, I want to 看到退款资格判断准确率, so that 我能评估错误售后承诺的经营风险。
27. As a 商家老板, I want to 看到该转人工场景的召回率, so that 高风险问题不会被自动化遗漏。
28. As a 商家老板, I want to 看到越权访问拦截率, so that 我能评估客户数据安全性。
29. As a 商家老板, I want to 看到平均处理时长和首字延迟, so that 我能估算客服效率收益。
30. As a 产品经理, I want to 用结构化场景数据维护评测案例, so that Markdown、Excel 和实现不会出现语义漂移。
31. As a 产品经理, I want to 为每个案例定义预期意图、资格、工具调用和转人工结果, so that 系统可以自动回归测试。
32. As a 产品经理, I want to 使用固定的 `policy_version`, so that 政策变更可以追溯并复现历史结果。
33. As a Agent 开发者, I want to 让模型只解释规则函数的结果, so that 模型不会自行编造退款资格。
34. As a Agent 开发者, I want to 让工具返回统一的成功和失败状态, so that 降级逻辑可以复用而不依赖具体工具实现。
35. As a Agent 开发者, I want to 在相同输入下重复运行同一评测案例, so that 我能稳定比较单 Agent 和多 Agent 的行为。
36. As a Agent 开发者, I want to 记录输入、检索、工具、决策和输出的 trace, so that 我能快速复盘 bad case。

## Implementation Decisions

### 范围与业务边界

- 第一版主场景冻结为：未发货或已发货未签收的订单，用户咨询退款/退货资格。
- 换货、退款进度、已签收后退货、物流投诉和支付/开票问题只做意图识别和正确引导，不进入自动资格判断闭环。
- Agent 只读，不执行退款、改单、发券、关闭售后单或其他订单写操作。
- 不承诺赔付金额、具体到账时效或平台法律结论。
- 使用一个虚构综合生活用品店和固定的 `policy_v1.0`，避免不同平台规则造成不可复现的判断。
- 商品至少覆盖普通实物、定制商品、易腐/贴身特殊商品三类。

### 唯一集成 seam

- 建立一个客服请求编排入口，接收用户消息、系统注入的 `user_id`、可选 `order_id`、会话上下文和运行模式开关。
- 该入口负责调用意图识别、RAG、工具、决策和人工交接模块，并返回统一结构化结果与 trace。
- 单 Agent 与多 Agent 必须复用该入口及其外部契约；差异只体现在内部编排方式。

### 意图识别

- 第一版意图枚举固定为：退款/退货资格咨询、发起退货或退款请求、换货请求、退款进度查询、物流异常或未收到货、其他/无法识别。
- 意图识别必须输出 `intent` 与 `intent_confidence`。
- 置信度低于 `0.85` 时先进行一次澄清；澄清后仍低于阈值则转人工。

### 订单定位与身份校验

- `user_id` 必须来自登录态或系统上下文，模型不能从用户文本中自行生成或覆盖。
- 所有订单事实查询执行 `user_id + order_id` 联合校验。
- 没有订单号时先进行一次澄清；在安全条件满足时，由查订单能力返回当前用户最近 3 笔脱敏订单供选择。
- 最多追问两次；第三次仍无法定位有效订单时转人工。
- `not_found`、`forbidden`、`invalid_argument` 不自动重试，也不能被解释成退款资格结论。

### RAG 知识库

- 第一版仅纳入四类版本化文档：退款/退货政策、商品类目例外规则、物流状态说明与 FAQ、人工转接规范与客服边界。
- 检索结果必须包含片段内容、来源标识、相似度或排序信息和 `policy_version`。
- RAG 只能提供政策证据和解释材料，不能直接产出资格结论。
- 政策自然语言文档与结构化规则表使用相同的 `policy_version` 关联。

### 三个只读工具

- 查订单：返回支付状态、商品信息、商品类目/特殊属性、下单时间、订单状态、用户归属和必要的售后关联字段；订单号为空时返回当前用户最近订单的脱敏摘要。
- 查物流：返回发货时间、当前物流状态、最近更新时间、是否签收和物流异常标记。
- 查售后：返回是否存在售后单、售后类型、售后状态、申请时间、重复申请或历史限制标记。
- 三个工具都接收系统注入的 `user_id`、可选 `order_id` 和 `request_id`，服务端再次校验权限。
- 工具统一返回 `success`、`not_found`、`forbidden`、`invalid_argument`、`timeout`、`upstream_error`、`data_incomplete` 七种状态，并提供数据、错误码、错误说明、耗时和数据源标识。
- `timeout` 和 `upstream_error` 最多自动重试一次；权限、参数、找不到数据等状态不重试。
- 全链路超过 8 秒，或重试后关键数据仍不可用，必须停止调用并转人工。

### 规则决策

- 决策函数接收订单、物流、售后事实、商品属性和版本化政策规则，输出资格结果和命中的规则标识。
- 资格结果固定为 `eligible`、`ineligible`、`unknown`。
- 未发货、已支付、普通商品、无进行中售后单时为 `eligible`。
- 对上述 `eligible` 结果，`next_action` 应包含展示“申请退款”按钮的指令；按钮只生成待人工确认的退款草稿，不执行真实退款。
- 已发货未签收、已支付、普通商品、物流状态正常时为 `eligible`，但下一步只能生成待人工确认的售后草稿。
- 政策明确排除的定制、易腐、贴身或其他特殊商品为 `ineligible`。
- 已有进行中的售后单、重复申请、关键事实冲突、字段缺失或政策未覆盖时为 `unknown` 并转人工。
- 未支付订单不进入退款资格判断，应说明尚未产生可退款支付。
- 模型不能修改规则结果，也不能依据自然语言自行推断未被决策函数返回的条件。

### 统一输出

- 编排入口返回 `intent`、`intent_confidence`、`eligibility`、`evidence`、`policy_version`、`next_action`、`need_human`、`handoff_reason`、`draft_for_human` 和 `trace_id`。
- 当结果为已支付且未发货的可退款订单时，响应还必须表达可展示的消费者动作 `申请退款`；动作执行结果只能是本地模拟或待人工确认草稿。
- 面向消费者的回答使用“结论—依据—下一步”三段式，并隐藏内部错误细节、置信度和调试字段。
- 面向商家的调试面板展示结构化字段、RAG 来源、工具状态、规则命中、追问次数、降级原因和耗时。
- 资格不确定时必须明确说“暂时无法判断”，不得使用“大概率可以”等模糊承诺。

### 人工交接

- 以下情形强制转人工：身份或权限不匹配、连续两次无法定位订单、工具重试后失败、关键数据缺失或冲突、特殊商品例外、进行中的售后或重复申请、金额争议、强烈负面情绪/投诉、用户明确要求人工、低置信度澄清失败。
- `draft_for_human` 至少包含用户原话、识别意图、用户与订单标识、订单/物流/售后事实摘要、政策版本、已追问问题、失败原因、情绪信号和建议人工动作。

### 数据与模式开关

- 场景主数据以结构化 JSON/CSV 为唯一事实源；Markdown 用于说明，Excel 用于查看或导出，不能各自维护不同标签。
- 初始模拟数据覆盖约 20–30 个用户和 40–60 个订单，包含正常、例外、越权、缺失、冲突、超时和重复售后数据。
- `MCP_ENABLED` 和 `MULTI_AGENT_ENABLED` 作为独立开关保留；第一版可先使用本地函数工具，后续再替换为 MCP 适配器。
- 多 Agent 对比版使用编排 Agent、政策 Agent、事实 Agent、人工交接 Agent 四个角色；政策 Agent 不下资格结论，事实 Agent 不解释政策。

## Testing Decisions

- 测试最高 seam 是客服请求编排入口，优先验证外部行为和完整链路，不绑定具体 prompt、框架或内部类名。
- 所有 60 条案例使用确定性的模拟工具和固定政策版本，支持重复运行并生成结构化断言。
- 每条案例至少断言：意图、资格结果、工具调用顺序、权限行为、是否转人工、转人工理由、只读约束和降级行为。
- 测试集分布：约 30 条正常路径、15 条政策例外、10 条权限/数据/工具失败、5 条多轮或情绪升级。
- 必测场景包括：未发货普通商品、已发货未签收、定制商品、未支付订单、错误订单号、越权订单号、无订单号两次追问、最近订单选择、已有售后单、重复申请、工具超时、上游错误、数据缺失、事实冲突、换货、退款进度、物流异常和明确要求人工。
- 安全与高风险测试优先于文案测试：错误退款资格结论零容忍，越权访问拦截率必须为 100%。
- 第一版验收阈值：意图识别准确率至少 90%，应转人工场景召回率至少 95%，越权拦截率 100%，工具失败降级成功率 100%，首字延迟低于 2 秒，单轮总耗时低于 8 秒。
- 额外记录单 Agent 与多 Agent 的结果一致性、总耗时、首字延迟、模型调用次数、token、工具调用次数和失败可定位性。
- 通过结构化结果断言后，再进行人工抽样检查回答是否清楚、依据是否可理解、下一步是否可执行以及是否泄露敏感信息。

## Out of Scope

- 真实电商平台、真实订单、真实用户身份和真实支付系统接入。
- 自动执行退款、退货单创建、换货、改单、发券、赔付或其他写操作。
- 已签收后退货的完整逆向物流流程。
- 真实退款到账、支付、开票、投诉和平台仲裁流程。
- 覆盖所有平台或商家的通用退款法律规则。
- 生产级长期记忆、跨会话用户画像和复杂营销推荐。
- 在第一版中追求多 Agent 必然优于单 Agent，或以聊天拟人度作为主要成功标准。
- 在没有结构化证据、政策版本或权限校验的情况下给出退款承诺。

## Further Notes

- 该 spec 是从已确认的产品对齐结果整理而来，当前工作区仍需后续实现原型代码、模拟数据、结构化场景主数据和评测运行器。
- 建议实现顺序为：结构化输出与 trace → 意图识别基线 → RAG → 三个只读工具 → 规则决策 → 多轮追问与失败降级 → 人工交接 → 商家调试面板 → 多 Agent 对比 → 60 条评测回归。
- 政策文档、结构化规则和评测案例必须在每次政策变更时同步更新版本号；历史 trace 仍保留其当时使用的政策版本。
- 调试面板中的 `user_id`、手机号、地址和其他个人信息必须脱敏；订单号可用于关联，但在消费者界面不展示不必要的内部标识。
- 主演示建议固定为六段：正常未发货、已发货未签收、特殊商品例外、错误/越权订单、工具失败或数据缺失、两次追问后人工交接。
- 当前没有已配置的项目 issue tracker 或 triage label 词汇，因此本次将 spec 发布为项目内 Markdown 文档；后续完成项目 tracker 配置后，可将本文同步为带 `ready-for-agent` 标签的 issue。

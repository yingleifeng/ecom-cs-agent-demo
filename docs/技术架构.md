# 电商商家客服 AI Agent Demo 技术架构

**版本**：v0.1  
**定位**：学习型、可交互、可评测的单体原型  
**关联文档**：[PRD](PRD.md)、[第一版 Spec](客服AI%20Agent第一版Spec.md)、[任务票据](../../.scratch/客服AI-Agent第一版/issues/01-可运行原型骨架与客服编排入口.md)

## 1. 架构目标

这不是生产级电商平台，而是一个用于学习和演示的 Agent 原型。因此架构优先级是：

1. 能在个人电脑上启动和演示。
2. 每一层职责清楚，便于理解 RAG、工具调用、记忆和 Agent 编排。
3. 所有判断可追踪、可测试、可复现。
4. 先用最少组件跑通主链路，再通过开关演进到 MCP 和多 Agent。
5. 不把模型输出直接连接到退款等写操作。

## 2. 总体方案

采用“模块化单体（modular monolith）”架构：一个 Python 应用、一个客服请求入口、若干职责明确的模块。第一版不拆微服务，不引入消息队列、复杂数据库或 Kubernetes。

```text
消费者聊天界面 / 商家调试界面
              │ HTTP 或本地调用
              ▼
      客服请求编排入口（唯一集成 seam）
              │
      ┌───────┼────────┬────────┬─────────┐
      ▼       ▼        ▼        ▼         ▼
   意图识别  短期记忆  RAG检索  只读工具  规则决策
                                  │
                        订单 / 物流 / 售后
                                  │
                         模拟数据适配器
              │
              ▼
       降级与人工交接 → 统一响应 + trace
```

后续演进：

```text
本地函数工具 ──(MCP_ENABLED)──> MCP Server
单 Agent     ──(MULTI_AGENT_ENABLED)──> 多 Agent 编排
会话短期记忆 ──> 跨会话长期记忆（第一版之后）
```

## 3. 推荐技术栈

| 层 | 第一版选择 | 选择理由 |
|---|---|---|
| 语言 | Python 3.11+ | AI/数据生态成熟，适合初学者和快速原型 |
| API | FastAPI | 类型友好、自动生成接口文档，适合作为唯一编排入口 |
| 演示 UI | Streamlit | 用少量 Python 快速实现聊天窗口和调试面板 |
| 数据校验 | Pydantic | 用模型定义统一输入、输出、工具 envelope 和 trace |
| RAG | 本地 Markdown + 简单向量检索 | 透明、低成本，便于理解切块、召回和引用 |
| 模型 | 通过环境变量配置的兼容 Chat Completions/Responses 客户端 | 可替换模型，不把供应商写死在业务层 |
| 模拟数据 | JSON/CSV | 人可读、可版本控制，适合 20–30 用户和 40–60 订单 |
| 测试 | pytest | 覆盖规则、工具、编排入口和评测运行器 |
| 配置 | `.env` + Pydantic Settings | 管理模型、模式开关和超时参数 |
| 日志 | Python logging + JSON trace | 够用且容易在本地查看 |

第一版可以先只提供 CLI 或 FastAPI 接口，再接 Streamlit；UI 不应反过来决定 Agent 的核心设计。

## 5. 核心模块职责

### 5.1 客服请求编排入口

这是最高层、也是主要测试 seam。它接收：

- `message`：用户当前消息
- `user_id`：系统注入的登录用户，不信任用户文本
- `order_id`：可选订单号
- `session_id`：会话标识
- `mode`：单 Agent / 多 Agent、local / MCP

它按以下顺序协调模块：

1. 从短期记忆读取当前会话状态。
2. 识别意图和置信度。
3. 处理订单号槽位和追问上限。
4. 校验 `user_id + order_id`。
5. 检索相关政策。
6. 调用订单、物流、售后三个只读工具。
7. 调用版本化退款规则函数。
8. 生成消费者回复和必要的人工交接摘要。
9. 写入 trace 并返回统一响应。

编排器负责流程，不负责自行编写退款业务规则。

### 5.2 意图识别

第一版固定六类意图：

```text
refund_eligibility
refund_request
exchange_request
refund_status
logistics_issue
unknown
```

模型可以识别意图，但低于 0.85 置信度时必须澄清；澄清后仍低于阈值就转人工。意图识别结果必须结构化，不能只返回自然语言。

### 5.3 RAG 检索

RAG 知识库只包含：退款/退货政策、商品例外规则、物流 FAQ、人工转接规范。

RAG 模块分为三步：

1. 文档加载和切块。
2. 本地索引和 Top-K 检索。
3. 返回片段、来源、相似度/排序和 `policy_version`。

RAG 的职责是找证据和帮助解释，不直接决定 `eligible`、`ineligible` 或 `unknown`。

### 5.4 只读工具层

工具层先实现本地函数，后续增加 MCP 适配器。三个工具为：

- `get_order`：订单状态、支付状态、商品属性和用户归属
- `get_logistics`：发货、签收、物流状态和异常标记
- `get_after_sales`：售后单、状态、重复申请和历史限制

统一输入：

```json
{
  "user_id": "u_001",
  "order_id": "o_001",
  "request_id": "req_001"
}
```

统一返回 envelope 的关键字段：

```text
status: success | not_found | forbidden | invalid_argument | timeout
        | upstream_error | data_incomplete
data: 工具白名单数据
error_code: 可选
latency_ms: 工具耗时
source: 数据源标识
```

服务端负责权限校验；模型不能修改 `user_id`。超时和上游错误最多重试一次，其他失败不重试。

### 5.5 规则决策层

规则函数读取结构化政策和工具事实，输出：

- `eligibility`: `eligible` / `ineligible` / `unknown`
- `matched_rule_id`
- `policy_version`
- `reason_codes`

规则函数是退款资格的唯一决策者。模型只能把规则结果组织成用户可理解的话术。对“已支付 + 未发货 + 普通商品 + 无进行中售后单”的结果，规则层还返回可展示动作 `request_refund`；该动作只进入本地模拟的待人工确认草稿，不连接任何真实写接口。

### 5.6 短期记忆

第一版需要短期记忆，但只保存当前会话流程状态：

- 当前意图
- 当前订单号
- 已确认的槽位
- 追问次数
- 已查询工具结果摘要
- 用户最近一句相关诉求

短期记忆建议先用内存字典实现，接口设计成可替换存储。订单、物流和售后事实仍以工具实时查询为准，不能从记忆中恢复为权威事实。

### 5.7 长期记忆

长期记忆不属于第一版完成条件。后续可以保存用户明确同意且跨会话有价值的信息，例如尺码偏好或沟通偏好；不得保存支付信息、一次性验证码等敏感数据，也不能直接改变退款规则结果。

### 5.8 降级与人工交接

降级模块统一处理：权限失败、订单定位失败、工具失败、关键数据缺失、事实冲突、特殊商品、金额争议、情绪升级和用户要求人工。

人工交接摘要包含用户原话、意图、订单和查询结果、政策版本、追问历史、失败原因、情绪信号和建议动作。

### 5.9 Trace 与隐私

每次请求生成 `trace_id`，记录：

- 原始输入（敏感内容脱敏）
- 意图和置信度
- RAG 命中片段及来源
- 工具入参摘要、出参状态和耗时
- 规则命中
- 最终响应
- 降级/转人工原因
- TTFT 和总耗时

手机号、地址、支付信息和其他个人信息只保存脱敏值或哈希。消费者界面不展示内部 trace。

## 6. 端到端数据流

```text
用户消息 + 系统 user_id
        │
        ▼
编排入口读取短期记忆
        │
        ├─ 意图低置信度？──是──> 澄清 / 第二次失败后人工
        │
        ├─ 无 order_id？──────> 追问 / 最近订单选择
        │
        ├─ 权限不通过？───────> 禁止泄露 + 人工
        │
        ├─ RAG 检索政策
        ├─ get_order
        ├─ get_logistics
        └─ get_after_sales
                │
                ▼
        规则决策函数
                │
        ├─ eligible
        ├─ ineligible
        └─ unknown ───────────> 人工交接摘要
                │
                ▼
      三段式回答 + trace + 更新短期记忆
```

## 7. 关键设计原则

1. **模块化单体优先**：小 demo 不需要微服务；先保证调用链可读。
2. **事实、政策、决策分离**：工具查事实，RAG 找政策，规则函数下结论，模型负责表达。
3. **只读优先**：任何写操作都不暴露给模型。
4. **统一契约**：本地工具和 MCP 工具、单 Agent 和多 Agent 复用同一输入输出。
5. **安全默认**：不确定就 `unknown` 并人工，不以模型自信程度替代证据。
6. **可观测优先**：没有 trace 就无法解释 bad case，也无法比较技术方案。
7. **最高 seam 测试**：以客服请求编排入口做端到端行为测试，内部模块再补少量单元测试。

## 8. 开发阶段

| 阶段 | 交付 | 对应票据 |
|---|---|---|
| 0 | 项目骨架、配置、结构化输出、trace、CLI/API | 01 |
| 1 | 意图识别和非主流程分流 | 03 |
| 2 | 政策文档、RAG、模拟数据、规则判断 | 02 |
| 3 | 订单/物流/售后工具、安全校验和降级 | 05 |
| 4 | 短期记忆、多轮追问和人工摘要 | 04、05 |
| 5 | 商家调试面板和脱敏 | 06 |
| 6 | 60 条评测和自动验收 | 07 |
| 7 | MCP 本地/远程工具对比 | 08 |
| 8 | 多 Agent 对比 | 09 |
| 9 | 完整演示和回归 | 10 |
| 后续 | 长期记忆 | 11 |

每个阶段完成后都要运行已有评测，记录分数和 bad case；不要等所有代码完成后才第一次测试。

## 9. 本地运行形态

建议提供三种入口，按复杂度递增：

```text
python -m customer_agent.cli       # 最适合调试单个案例
uvicorn customer_agent.api:app     # API 和自动接口文档
streamlit run app.py               # 消费者聊天 + 商家调试面板
```

模型密钥、模型名称、`MCP_ENABLED`、`MULTI_AGENT_ENABLED` 和超时值全部通过 `.env` 配置。没有模型密钥时，应提供 deterministic mock mode，让规则和评测仍可运行。

## 10. 验收重点

- 主流程能从一条用户消息走到结构化资格结果。
- 任何越权、关键数据缺失或工具失败都不会产生肯定退款结论。
- trace 能还原一次请求的意图、RAG、工具、规则、降级和耗时。
- 60 条评测可重复运行。
- 单 Agent、本地工具是默认基线；MCP、多 Agent 和长期记忆通过后续阶段加入。

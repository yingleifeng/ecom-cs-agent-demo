# 知识库结构与 RAG 资产

## 1. 知识库目录

```text
data/knowledge/
├── refund_policy_v1.0.md
├── product_exception_rules_v1.0.md
├── logistics_faq_v1.0.md
└── handoff_guidelines_v1.0.md
```

每份文档都使用固定版本号和稳定的二级标题。切块时保留文档名、版本、标题和 `chunk_id`，便于引用和回溯。

## 2. 文档职责

| 文档 | 回答什么 | 不负责什么 |
|---|---|---|
| 退款政策 | 普通商品在不同订单状态下的政策 | 不查询实时订单 |
| 商品例外 | 定制、易腐、贴身等例外 | 不覆盖用户权限 |
| 物流 FAQ | 物流状态含义和异常解释 | 不替代实时物流工具 |
| 人工规范 | 哪些情况必须转人工、如何交接 | 不决定退款资格 |

## 3. RAG 流程

```text
Markdown 文档
  → 按二级标题切块
  → 为每个 chunk 生成词频向量
  → 写入 LocalVectorStore
  → 查询向量化
  → cosine similarity Top-K 召回
  → 返回 chunk_id、标题、来源和相似度
  → 编排器把政策片段放入 evidence
```

当前实现使用本地透明的词频向量，目的是让初学者能看懂索引和召回；后续可以替换 embedding 和向量数据库，不能改变 `Evidence` 外部契约。

## 4. Chunk 设计规则

- 一个二级标题下的完整段落作为最小业务 chunk，避免把条件和结论拆开。
- 每个 chunk 必须包含一个可引用的政策观点，不写无意义的目录或标题。
- `chunk_id` 在同一文档版本内稳定，政策修订时更新版本号。
- 检索不到相关 chunk 时不得编造政策，应返回未知并转人工或请求补充信息。
- 召回结果只提供证据，资格结果仍由结构化规则函数产生。
